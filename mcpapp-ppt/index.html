Part 0 · 开篇 · 为什么需要

纯文本对话的三个局限

模型能想清楚，但界面只有一个输入框

01

选项只能靠打字回复

模型列出 1/2/3 个候选主题，用户还得手打编号或名称，容易打错，模型也要再解析一轮。

02

图表数据挤占上下文

让模型输出 ECharts option，大段 JSON 进上下文，浪费 token，还可能被模型改错数字。

03

复杂交互无从表达

表单填写、确认、预览、跳转 ERP 这类操作，文字描述再多也替代不了一个按钮。

MCP App 的答案：模型负责判断“什么时候需要界面、传什么参数”，界面由前端组件自己渲染、自己取数、自己把结果交回模型。

Part 1 · 概念与架构 · 定义

MCP App 是什么

运行在灵基 WebUI 沙箱 iframe 中的静态前端应用

🧩

静态前端

React + Vite 构建出的 dist/，上架后由宿主从 CDN 加载进沙箱 iframe。UI 统一用 lingee-ui / lingee-icon。

🔌

AppBridge 双向通信

宿主与 App 之间走 PostMessage。App 用官方 SDK @modelcontextprotocol/ext-apps 的 useApp 接线，不手写协议。

🎯

虚拟入口工具

每个 App 以 appCode 为名注册一个“虚拟工具”。模型调用它，宿主就把 App 拉起，并把入参注入进去。

一句话：对模型来说它是一个工具，对用户来说它是一块界面，对开发者来说它是一个普通的前端项目。
Part 1 · 概念与架构 · 运行架构

运行架构

调用即返回，App 独立运行，用户操作作为新一轮输入回到 harness

Harness按 SKILL.md 决定何时调
宿主 WebUI拉起 · 代理 · 浮层
MCP App沙箱 iframe
工具层业务工具 / platform_*
第 N 轮 loop
1调用虚拟入口工具 appCode
2立即返回，不等 App
3拉起 iframe，ontoolinput
4结束本轮输出（由 prompt 控制）
loop 已释放 · App 在 iframe 里独立运行，等用户操作多久都不占用 loop
5渲染界面，用户交互
6callServerTool（经宿主代理）
7返回结果
第 N+1 轮 loop · 由用户操作触发
8updateModelContext 等同用户发起一次新提问
9继续推理、回复用户
调用返回
不阻塞 loop：入口是虚拟工具，调用即返回；本轮是否收尾由 prompt 控制（如 nl2sql 规定“调用后停止本轮输出”），而不是 harness 在等 App；用户的操作结果经 updateModelContext 作为新一轮输入回到 harness。
Part 1 · 概念与架构 · 生命周期

一次调用的生命周期

从模型发起调用，到 App 被销毁

模型调用虚拟入口工具
↓
宿主拉起 iframe，与 App 握手下发 hostContext → onhostcontextchanged
↓
入参流式到达 ontoolinputpartial（可多次）JSON 可能不完整，保留上一帧，不清空
↓
完整入参到达 ontoolinput首屏只认它；副作用只在这里做一次
↓
渲染 → 用户交互 → callServerTool 取数 / 落库
↓
把结果交回模型 updateModelContext
↓
onteardown 清理
注意：入口是虚拟工具，很多场景没有输出，ontoolresult 可能永远不来，首屏不能挂在它上面等。

Part 2 · 能力全景 · 宿主 → App

宿主 → App：六个回调

全部注册在 useApp 的 onAppCreated 里，写在 useEffect 会漏掉首发通知

回调触发时机该怎么用
ontoolinputpartial模型流式生成入参期间，可能多次解析不出来就保留上一帧；不做任何副作用
ontoolinput入参生成完毕首屏渲染入口；发授权、取数等副作用只在这里做一次
ontoolresult入口工具有输出时可能永远不来，只作兜底
ontoolcancelled调用被取消展示取消态
onhostcontextchanged握手后、容器尺寸 / 显示模式变化参数是增量，现场 getHostContext() 读全量，比对后再 setState
onteardownApp 被销毁前清理定时器、订阅
接线骨架
const { app, isConnected } = useApp({
  appInfo: { name: "my-app", version: "1.0.0" },
  capabilities: {},
  onAppCreated: (instance) => {
    instance.ontoolinputpartial = (p) => applyPayload(p.arguments, true);
    instance.ontoolinput = (p) => applyPayload(p.arguments, false);
    instance.onhostcontextchanged = () => setHostCtx(instance.getHostContext());
  },
});
Part 2 · 能力全景 · hostContext

hostContext：宿主给的环境快照

握手时下发；运行期只有 displayMode 与 containerDimensions 会变

🎨 theme / styles

styles.variables 是 76 个已解析的 Design Token 字面量，需调 applyHostStyleVariables 写到根节点才生效。

📐 containerDimensions

容器尺寸。JS 里要按宽度分支时读它，不要去摸宿主页面；sidebar 模式才下发可用高度。

🖥 displayMode / runMode

inline ↔ fullscreen 的当前状态，以及 info.json 声明的运行模式。

🛡 tools

当前 App 被放行的工具白名单。可据此判断某个业务工具是否已上线，避免必然失败的调用。

👤 bootstrap

用户、租户、会话 ID、界面语言。除 authRoles 外都可能是 null，且切语言后不会更新。

💡 写样式的姿势

自有样式统一写 var(--token, 兜底值)，没注入时也能看。

案例对照：主题澄清组件用了 Token 注入、tools 白名单探测和 bootstrap.bootstrapLanguage。
Part 2 · 能力全景 · App → 宿主

App → 宿主：出站能力

都要等 isConnected 为 true 再调，早调可能丢请求

方法作用失败形态
callServerTool调业务工具或平台工具不在白名单 → isError；后端代理失败 → reject
updateModelContext把交互结果交给模型继续处理返回 { isError }；文本或 additional 为空时静默丢弃
sendMessage以用户消息发进对话，触发模型回复返回 { isError }
openLink在宿主里打开外部链接返回 { isError }
downloadFile经宿主下载（沙箱拦截直接下载）返回 { isError }
requestDisplayMode请求 inline / fullscreen返回宿主实际设置的模式
sendSizeChanged上报内容尺寸SDK autoResize 默认已做，通常不用手动调
sendLog / requestTeardown打日志 / 主动关闭自己notification，无返回
实践建议：把 callServerTool 包一层，isError 转成异常，外层统一 try / catch，两种失败形态一起兜住。
Part 2 · 能力全景 · 平台工具

平台工具集 platform_*

宿主统一提供、所有 App 共享，不用在 info.json 里登记

💾 App 状态

  • platform_save_app_state 按（会话, 消息）落库，覆盖写
  • platform_get_app_state 启动时恢复

📎 会话文件

  • platform_list_session_attachments 用户上传的附件
  • platform_list_session_artifacts 对话产出的文件

🏢 环境与授权

  • platform_get_erp_environment 当前绑定的 ERP
  • platform_get_authorization_code 免登授权码（60 秒一次性）
  • platform_is_mobile 宿主是否移动端布局

🪟 宿主浮层

  • platform_show_confirm / platform_show_toast
  • platform_open_modal / platform_open_sidebar 把 App 自己的页面开成弹窗或侧栏
为什么状态必须落库：宿主同时存活的 App iframe 有上限（当前 5 个），超出会淘汰最久未活跃的那个，重新进入视口时从头初始化，内存状态全丢。

Part 2 · 能力全景 · 安全与边界

安全与边界

沙箱换来的是安全，代价是一些“不能直接做”的事

工具白名单
  • 业务工具必须登记在 mcpConnector[].relateTools，未登记直接被宿主拒绝
  • 平台工具 platform_* 不受白名单约束
沙箱限制
  • 直接下载被拦 → 走 downloadFile
  • 外部资源受 CSP 约束 → 资源尽量内联
  • 宿主点击不传进 App → “点外部关闭”需监听 blur 兜底
  • iframe 只能盖住自己 → 确认框 / 弹窗交给宿主渲染
上架包约束
  • zip 一级目录正好是 dist/ + info.json
  • 不超过 5 MB，mermaid 这类重依赖要懒加载或去掉
  • 扩展名白名单 22 种，.wasm、.md、无后缀文件会被拒
  • 生产构建建议关掉 sourcemap
临时会话
  • 首轮对话会话 ID 为 local_ 前缀，查询类平台工具返回空、写入类失败，要能静默降级

什么时候弹出这张卡片

档位score
高度一致90 ~ 100
明显相关60 ~ 89
弱相关30 ~ 59
不相关0 ~ 29（不返回）
断档指相邻候选不在同一档，与分差大小无关。
nl2sql 调 selectSubjects
↓
top1 < 60？
是 → 引导用户用「选择主题」控件手动选
↓ 否
只有 1 个候选，或 top2 断档？
是 → 直接采用 top1，不打扰用户
↓ 否（top1、top2 同档）
调用主题澄清组件
candidates = 与 top1 同档的全部候选

常见问题

点击展开查看回答

Q1：MCP App 和普通 MCP 工具有什么区别？

普通工具返回数据给模型，由模型用文字转述。MCP App 返回的是一块界面：模型只负责决定何时调用、传什么参数，渲染、取数、交互都在前端完成，必要时再把结果交回模型。

Q2：App 能直接调后端接口吗？

不能直连。所有调用经 callServerTool → 宿主代理，业务工具必须登记在 info.json 的 relateTools 白名单里。外部资源也受宿主 CSP 约束。

Q3：用户在 App 里的操作，模型怎么知道？

用 updateModelContext：文本作为一条用户消息展示在对话里，structuredContent.additional 作为补充上下文只给模型读。需要模型立刻回复时也可以用 sendMessage。

Q4：刷新页面后 App 里的状态还在吗？

内存状态不在。需要保留的用 platform_save_app_state 按（会话, 消息）落库，启动时 platform_get_app_state 恢复。首轮临时会话（local_）写入会失败，要能静默降级。

Q5：需要弹窗或表单时怎么办？

纯文本确认用 platform_show_confirm；带表单、列表的用 platform_open_modal 或 platform_open_sidebar，把 App 自己的另一个页面开成弹窗或侧栏。承载页没有 AppBridge，数据靠 params 进、result 出。

Q6：一个 App 能同时支持 message 和 sidebar 吗？

runMode 写在 info.json 里，一个 appCode 只有一种。同一份代码可以上架成两个 appCode 分别验证，各配一份 SKILL.md。
